# PayProof AI — Feature Plan and Delivery Checklist

**Product promise:** Help small online sellers turn scattered order messages and payment updates into a reviewable workflow—without confusing AI suggestions with proof of payment.

**Current stage:** Active prototype using PayPal Sandbox. The dashboard contains illustrative records. Do not represent sample records as live customer or transaction data.

## Product principles

1. **PayPal is the payment source of truth.** AI, browser redirects, screenshots, receipts supplied by customers, and customer claims cannot mark an order as paid.
2. **Server-side verification only.** Verify the PayPal order and capture status, order ID, capture ID, expected reference, amount, and currency on the server.
3. **Human review for ambiguity.** Unmatched products, missing quantities, conflicting details, and uncertain AI output must stop for review.
4. **Server-owned prices.** Never accept a price or total generated by an AI model or supplied by the browser.
5. **Honest interface states.** Clearly distinguish illustrative demo data, pending payments, verified payments, failed attempts, and records requiring investigation.
6. **Privacy by default.** Store only necessary order/payment metadata. Never log secrets or unnecessary payment details.

## Feature 1 — AI Order Assistant

**Goal:** Turn a customer's free-text request into a structured, reviewable order draft.

### Expected workflow
1. Seller pastes the original customer message.
2. Server-side model extracts only supported product names, quantity, and missing-information notes.
3. Server validates the response against a strict schema and product allowlist.
4. Unsupported products, missing quantities, quantities outside the allowed range, malformed responses, and provider failures are rejected or flagged.
5. Seller reviews and confirms the draft.
6. A trusted server-side catalogue calculates the amount before any checkout is created.

### Acceptance criteria
- AI output is advisory and never saves an order automatically.
- Product and quantity are validated again on the server before checkout.
- Model output cannot set a price, create a PayPal payment, or change payment status.
- Missing or ambiguous details require clarification.
- Provider timeout, invalid JSON, and unavailable configuration fail safely.
- Add tests for valid requests, missing product, missing quantity, unknown product, invalid quantity, malformed provider output, and provider errors.

**Status:** Server-side extraction calls an AI Gateway-compatible model endpoint, validates structured output, caps input size, and times out after 15 seconds. The UI remains advisory-only. The required AI Gateway key/model are not confirmed in the Vercel project environment, so live model responses remain unverified. Route-level tests and live provider error tests remain outstanding.

## Feature 2 — AI Payment Investigator

**Goal:** Explain payment discrepancies using verified transaction evidence.

### Inputs
- PayPal order ID or an internally recorded order reference.
- Expected order amount/currency and expected reference from trusted server-side order data.
- PayPal order/capture details retrieved server-side.

### Checks
- Does the PayPal response belong to the requested order ID?
- Is the order status complete?
- Is there a capture, and is the capture status complete?
- Does the captured amount match the expected amount?
- Does the currency match?
- Do the trusted order reference and PayPal reference/custom ID match?
- Is the payment pending, incomplete, duplicated, or otherwise unresolved?

### Output
- **Verified:** all required deterministic checks passed.
- **Pending:** PayPal does not yet confirm a completed capture.
- **Review required:** missing, inconsistent, mismatched, or ambiguous evidence.
- A concise explanation of which checks passed or failed and what the seller should do next.

AI may summarize the verified check results in plain language. It must not invent evidence, override failed checks, or decide the payment state independently.

### Acceptance criteria
- Payment state is computed by server-side code, not by an LLM.
- Never expose PayPal client secrets or access tokens to the browser.
- A failed check cannot produce a verified state.
- Test mismatched order ID, amount, currency, reference, incomplete capture, missing capture, and PayPal API failure.
- Use recorded evidence for investigation; do not trust an arbitrary user-supplied ID without authorization and ownership checks.

**Status:** The dedicated investigator page is linked from the workspace navigation. Server-side checks require matching PayPal order ID, completed order, existing completed capture, expected amount/currency, and trusted reference/custom ID. The capture endpoint checks order identity/reference/amount/currency before attempting capture and uses a stable per-order request ID for retries. Eleven deterministic unit tests pass for successful evidence and incomplete, pending, mismatched, and unsuccessful cases. Live Sandbox end-to-end testing, route-level integration tests, internal order ownership checks, and persistence remain outstanding.

## Feature 3 — Payment Operations Dashboard

**Goal:** Show sellers what is happening and what needs attention.

### Dashboard elements
- Total orders.
- Verified payments.
- Awaiting/pending payments.
- Failed or review-required payments.
- Recent orders and transaction activity.
- Filters for status and time.
- A clear explanation for every flagged item.
- Links/actions to open an order's evidence and review history.

### Data rules
- Production metrics must be calculated from persisted, authorized records.
- Sample records must remain visibly labelled as demo data.
- Do not count a browser return, AI response, or checkout creation as a completed payment.
- Empty, loading, and error states must be designed explicitly.

**Status:** Dashboard layout and illustrative metrics exist. Live persistent data is not yet connected.

## Feature 4 — PayPal Sandbox Checkout and Verification

**Goal:** Demonstrate a complete, repeatable payment lifecycle using test money.

### Required path
1. Validate the reviewed order on the server.
2. Calculate the expected total from trusted product pricing.
3. Create a PayPal Sandbox order with a trusted reference.
4. Send the buyer to the PayPal approval URL.
5. Treat the return URL only as a signal to request server verification.
6. Capture the order server-side.
7. Verify order ID, order status, capture status, amount, currency, and reference.
8. Display the verified result or a clear review-required state.
9. Record the outcome and relevant identifiers without storing unnecessary sensitive data.

### Required negative tests
- User cancels checkout.
- Approval occurs but capture is not completed.
- PayPal returns a failed or incomplete capture.
- Requested order ID does not match PayPal's response.
- Amount, currency, or reference mismatch.
- Missing/invalid credentials or PayPal API outage.
- The capture endpoint is called repeatedly.
- A return URL is opened manually without a successful payment.

### Reliability requirements
- Use stable idempotency keys for retryable operations where supported.
- Handle an already-captured order by safely retrieving/checking its current state rather than blindly treating retries as a new payment.
- Before production, implement and verify PayPal webhook signatures and event idempotency.
- Sandbox success is not evidence of production readiness.

**Status:** Sandbox create/capture routes exist. Capture validates the order before state-changing capture and checks the returned evidence deterministically. Unit tests pass, but a successful end-to-end Sandbox payment and real negative-path API tests have not yet been confirmed.

## Feature 5 — Evidence and Audit Trail

**Goal:** Make every payment decision explainable after the event.

### Record fields (minimum necessary)
- Internal order ID and trusted reference.
- PayPal order ID and capture ID, when available.
- Expected amount/currency and PayPal-reported captured amount/currency.
- Verification result and individual check outcomes.
- Review reason and seller resolution, if applicable.
- Created/updated timestamps and event timestamps.
- Source of the event (server verification, verified webhook, or manual review).

### Requirements
- Store only the minimum necessary metadata.
- Do not store PayPal client secrets, access tokens, or full sensitive payment data.
- Prevent clients from writing a verified payment status directly.
- Make repeated webhook events and capture retries idempotent.
- Restrict access to order and audit information.
- Keep an audit history of status changes and review decisions.

**Status:** Persistent order/event records and audit history remain to be implemented.

## Environment configuration

Configure these only in Vercel's project environment settings or in a private local `.env.local` file:

- `PAYPAL_CLIENT_ID` — PayPal Sandbox REST app client ID.
- `PAYPAL_CLIENT_SECRET` — matching Sandbox secret.
- `PAYPAL_BASE_URL=https://api-m.sandbox.paypal.com` — Sandbox API.
- `APP_URL` — the URL for the environment being tested.
- `AI_GATEWAY_API_KEY` — server-side AI provider/Gateway key.
- `AI_MODEL` — model identifier supported by the configured gateway.
- `AI_GATEWAY_URL` — optional gateway endpoint if a non-default compatible endpoint is required.

Ensure variables are assigned to the environment being tested. Redeploy after changing Vercel environment variables. Never commit real values or use a `NEXT_PUBLIC_` prefix for secrets. Keep Sandbox credentials separate from any future live credentials.
